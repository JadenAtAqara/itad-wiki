# MQTT API

通过 MQTT 转出功能，您可以借助 MQTT Broker，以发布/订阅方式发送请求消息，调用 [已开放的数据转出 HTTP API](#调用-http-接口)。此外，您还可以实现 [心跳保活](#心跳与订阅续租)、[订阅或取消订阅设备数据](#订阅设备数据)，以及[接收设备数据变化和其他对象事件](#订阅事件)。

## 获取 MQTT 连接信息

在开始发布/订阅请求消息之前，您需要在 Aqara Studio 上启用 MQTT 转出服务，选择本地 Broker 或第三方 Broker，以此获取 MQTT 连接信息。相关流程请阅读 [以 MQTT 转出设备数据](./../../../aqara-studio/data-export-by-mqtt.mdx)。

## 鉴权

MQTT 通道身份认证和 Topic 访问权限由 Broker 的连接凭据与 ACL 负责。您无需使用 OpenAPI Token，也不需要发送 `AuthRequest` 消息进行身份认证。

对于生产环境，您应该配置 Broker ACL，使您的应用只能向分配给自己的请求 Topic 发布消息，并且只能订阅分配给自己的响应 Topic。

不要允许应用订阅 `/open/api/v1/response/+`。

## Topic

| Topic 类型 | 方向 | 格式 | 用途 |
| --- | --- | --- | --- |
| 请求 Topic | 应用到 Studio | `/open/api/v1/request/{clientId}` | API 请求、心跳、订阅和取消订阅消息 |
| 响应 Topic | Studio 到应用 | `/open/api/v1/response/{clientId}` | API 响应、订阅响应、推送消息和错误消息 |

:::tip
请求 Topic 和响应 Topic 开头的 `/` 是 Topic 名称的一部分，不能省略。
:::

格式中的 `{clientId}` 是您的应用在此 MQTT 通道中的逻辑会话和响应路由标识。常规情况下，一个 MQTT 连接对应一个应用，应用应使用其连接 Broker 时在 `CONNECT` 报文中提交的 MQTT Client ID 作为 Topic 中的 `{clientId}`。

格式中的 `{clientId}` 不是 Aqara Studio 在 **MQTT 转出**页面配置的 Client ID。Aqara Studio 使用自己的单个 MQTT 连接服务多个第三方应用，因此两者不应相同。只有代理程序通过一个 MQTT 连接承载多个逻辑客户端时，Topic 中的 `{clientId}` 才可以与该代理连接的 MQTT Client ID 不同；生产环境应通过 Broker ACL 限制每个应用可访问的请求和响应 Topic。

`clientId` 长度为 1～128 个字符，只能包含字母、数字、`.`、`_`、`:` 和 `-`。

## 服务质量（QoS） 

建议请求发布和响应订阅均使用 QoS 1。

发送请求前，您应先订阅响应 Topic，避免遗漏立即返回的响应。

## 调用 HTTP 接口

若要调用 以下已开放的数据转出 HTTP API：
- [空间相关接口](./../introduction.mdx#空间)
- [设备相关接口](./../introduction.mdx#设备)
- [自动化相关接口](./../introduction.mdx#自动化)

请编写并发送 `type` 为 `OpenApiRequest` 的请求消息。

### 请求字段

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| type | ✔ | string | 固定为 `OpenApiRequest`。 |
| version | ✔ | string | 固定为 `v1`。 |
| msgId | ✔ | string | 请求标识，响应使用相同的值。长度为 1～128 个字符，只能包含字母、数字、`.`、`_`、`:`、`@` 或 `-`。每个逻辑操作使用一个新值；重试同一操作时保持不变。 |
| data.method | ✔ | string | 支持 `GET`、`POST`、`PATCH` 或 `DELETE`。请根据上述各 HTTP API 文档选择合适的 HTTP 方法。 |
| data.path | ✔ | string | 传入上述 HTTP API 的 Endpoint，如 `/open/api/v1/devices`。  |
| data.query | ✘ | object | JSON 对象形式的查询参数。值可以是字符串、数字、布尔值或这些基础类型组成的数组，具体请参考各 HTTP API 文档中的 **Request - Query Parameters** 说明。 |
| data.headers | ✘ | object | 可选的 OpenAPI 元数据 Header，例如 `Lang`。不能包含 `Authorization` 或 Cookie；路由使用的 `ClientId` 取自 Topic，不能在此覆盖。 |
| data.body | ✘ | object \| null | JSON 请求 Body。接口没有请求 Body 时，此字段可以省略或传 `null`。具体请参考各 HTTP API 文档中的 **Request - Body** 说明。 |

### 请求示例

```json
{
  "type": "OpenApiRequest",
  "version": "v1",
  "msgId": "devices-001",
  "data": {
    "method": "GET",
    "path": "/open/api/v1/devices",
    "query": {
      "pageNum": 1,
      "pageSize": 20
    },
    "headers": {
      "Lang": "zh-CN"
    },
    "body": null
  }
}
```

### 响应说明

响应 Topic 会直接收到标准 HTTP OpenAPI 响应体，因此，您只需按照上述各 HTTP API 文档中的 **Responses** 说明解析响应体即可。

### 响应示例

```json
{
  "type": "GetDeviceInfoResponse",
  "version": "v1",
  "msgId": "devices-001",
  "code": 0,
  "message": "success",
  "data": {
    "totalCount": 1,
    "pageNum": 1,
    "pageSize": 20,
    "data": []
  }
}
```

## 心跳与订阅续租

MQTT 协议自身的 Keep Alive 用于维护客户端与 Broker 之间的连接。通常由 MQTT SDK 自动发送 `PINGREQ` 并处理 `PINGRESP`，不需要应用为了保持 Broker 连接而额外发布下面的 JSON `ping`。

本文的 `ping` 是 Studio 应用层的**逻辑订阅续租消息**，作用是告诉 Studio：该请求 Topic 对应的 `clientId` 仍在使用此前建立的数据订阅。请按以下规则使用：   
- 仅调用 OpenAPI、没有建立 [数据订阅](#订阅设备数据) 的客户端，不需要周期性发送 `ping`。
- 存在有效数据订阅时，发送到该 `clientId` 请求 Topic 的任意请求都会续期订阅；如果 30 秒内已经发送过其他请求，不需要再单独发送 `ping`。
- 有效订阅处于空闲状态、没有其他请求可用于续期时，建议每 30 秒内发送一次 `ping`。
- Studio 只根据请求 Topic 上收到的消息续期。客户端持续收到推送消息并不会自动续期订阅。
- 请求 Topic 连续 90 秒没有收到任何消息时，逻辑会话会过期，Studio 将清理该 `clientId` 的全部订阅并停止相关推送。之后再次发送 `ping` 只会创建新的逻辑会话，不会恢复已经清理的订阅；客户端必须重新发送相应的订阅请求。

MQTT Keep Alive 与 Studio 逻辑订阅续租相互独立，两者不能相互替代。客户端仍应根据所使用的 MQTT SDK 和 Broker 配置合适的 MQTT Keep Alive。

### 请求字段

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| type | ✔ | string | 固定为 `ping`。 |
| version | ✔ | string | 固定为 `v1`。 |
| msgId | ✔ | string | 请求标识，响应使用相同的值。长度为 1～128 个字符，只能包含字母、数字、`.`、`_`、`:`、`@` 或 `-`。每个逻辑操作使用一个新值；重试同一操作时保持不变。 |
| data | ✘ | null | 固定为 `null`。 |

### 请求示例

```json
{
  "type": "ping",
  "version": "v1",
  "msgId": "ping-001",
  "data": null
}
```

### 响应字段

收到对应的 `pong` 表示从客户端经过 Broker 到 Studio、再返回客户端的应用消息链路当前可用。若未收到 `pong`，客户端应先检查 MQTT 连接并保留原 `msgId` 重试；如果空闲时间可能已经超过 90 秒，应在链路恢复后重新订阅。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| type | string | 固定为 `pong`。 |
| version | string | 固定为 `v1`。 |
| msgId | string | 消息唯一标识。正常请求和响应使用相同 msgId 关联；解析失败、部分权限或内部异常可能返回 UNKNOWN；服务端推送由服务端生成，不等同于订阅请求 msgId。 |
| data | string | 固定为 `pong`。 |
| code | number | 响应状态码。0 表示成功，非 0 表示失败。 |
| message | string | 响应消息。 |

### 响应示例

```json
{
  "type": "pong",
  "version": "v1",
  "msgId": "ping-001",
  "data": "pong",
  "code": 0,
  "message": "success"
}
```


## 订阅设备数据

### 订阅全部或指定设备

使用 `SubscribeAllRequest`。`data` 为 `null`、省略或空数组时，订阅当前可访问的全部设备；传非空设备 ID 数组时，只订阅指定设备。

```json
{
  "type": "SubscribeAllRequest",
  "version": "v1",
  "msgId": "subscribe-devices-001",
  "data": ["device-001", "device-002"]
}
```

Studio 返回 `SubscribeAllResponse`。取消订阅时发送 `UnsubscribeAllRequest`：传设备 ID 数组可取消指定设备，`data` 为 `null` 或空数组时取消当前逻辑会话的全部设备数据订阅。

`SubscribeAllRequest` 会替换当前会话的 Trait 单项订阅。`UnsubscribeAllRequest` 只修改设备数据和 Trait 订阅；独立事件及对象事件必须使用各自的取消订阅消息。

### 订阅指定 Trait 值

```json
{
  "type": "SubscribeTraitValueRequest",
  "version": "v1",
  "msgId": "subscribe-trait-001",
  "data": [
    {
      "deviceId": "device-001",
      "endpointId": 1,
      "functionCode": "Light",
      "traitCodes": ["OnOff"]
    }
  ]
}
```

Studio 返回 `SubscribeTraitValueResponse`。取消指定 Trait 订阅时，使用相同的订阅项结构并将类型改为 `UnsubscribeTraitValueRequest`。订阅或取消订阅成功时 `code` 为 `0`，响应不包含 Trait 当前值。

## 订阅事件

### 告警事件

独立事件通道当前支持 `ALARM`：

```json
{
  "type": "SubscribeEventRequest",
  "version": "v1",
  "msgId": "subscribe-alarm-001",
  "data": ["ALARM"]
}
```

Studio 返回 `SubscribeEventResponse`。取消时发送 `UnsubscribeEventRequest`，并使用 `data: ["ALARM"]`。

### 对象事件

设备、空间及自动化变化通过对象事件订阅。`objectIds` 省略、为 `null` 或空集合时，表示订阅指定事件类型下当前可访问的全部对象。

```json
{
  "type": "SubscribeObjectEventRequest",
  "version": "v1",
  "msgId": "subscribe-object-001",
  "data": [
    {
      "eventTypes": ["SPACE_UPDATED", "AUTOMATION_UPDATED"],
      "objectIds": []
    }
  ]
}
```

Studio 返回 `SubscribeObjectEventResponse`。取消时发送 `UnsubscribeObjectEventRequest`，订阅项结构保持一致；`objectIds` 为空时，会移除指定事件类型下的全部对象规则。

`SubscribeObjectEventRequest` 接受以下事件类型：

- 设备空间关系：`DEVICE_SPACE_UPDATED`
- 空间：`SPACE_ADDED`、`SPACE_REMOVED`、`SPACE_UPDATED`
- 自动化：`AUTOMATION_ADDED`、`AUTOMATION_REMOVED`、`AUTOMATION_UPDATED`、`AUTOMATION_SPACE_UPDATED`

`objectIds` 非空时，同一个订阅项内的全部 `eventTypes` 必须属于同一对象类别；新增类事件只能订阅全部可访问对象。

## 推送消息

所有推送均发布到 `/open/api/v1/response/{clientId}`。

### Trait 值变化

```json
{
  "type": "TraitValueUpdate",
  "version": "v1",
  "msgId": "1754469720110",
  "data": [
    {
      "deviceId": "device-001",
      "endpointId": 1,
      "functionCode": "Light",
      "traitCode": "OnOff",
      "value": true,
      "time": 1754469720110
    }
  ],
  "code": 0,
  "message": ""
}
```

`value` 的类型由对应 Trait 定义决定，`time` 是毫秒级 Unix 时间戳。

### 对象事件

```json
{
  "type": "objectEvent",
  "version": "v1",
  "msgId": "object-event-001",
  "data": {
    "eventType": "SPACE_UPDATED",
    "objectId": "space-001",
    "time": 1754469720110,
    "data": {
      "spaceId": "space-001",
      "name": "客厅",
      "spatialMarking": "room"
    }
  },
  "code": 0,
  "message": "success"
}
```

内层 `data.data` 的结构由 `eventType` 决定。建议先根据 `eventType` 和 `objectId` 分发事件，再解析对应事件的数据内容。

设备数据订阅还可能收到 `DEVICE_ADDED`、`DEVICE_REMOVED`、`DEVICE_ENDPOINT_ADDED`、`DEVICE_ENDPOINT_REMOVED` 或 `DEVICE_TRAIT_PARAMETER_UPDATE` 类型的 `objectEvent` 推送。这些设备事件由 `SubscribeAllRequest` 或匹配的 Trait 订阅产生，不能用于 `SubscribeObjectEventRequest`。

### 告警事件

```json
{
  "type": "AlarmEvent",
  "version": "v1",
  "msgId": "alarm-notify-alarm-001",
  "data": {
    "uuid": "alarm-001",
    "deviceName": "漏水传感器",
    "deviceId": "device-001",
    "devicePointName": "漏水状态",
    "alarmClass": "critical",
    "alarmRuleName": "漏水告警",
    "alarmText": "检测到漏水",
    "alarmValue": "true",
    "sourceState": "active",
    "alarmTime": 1754469720110,
    "localized": {}
  },
  "code": 0,
  "message": "success"
}
```

### 错误响应

消息格式错误、消息类型不支持、路由未开放或业务处理失败时，返回 `ErrorMessage`：

```json
{
  "type": "ErrorMessage",
  "version": "v1",
  "msgId": "devices-001",
  "data": null,
  "code": 400,
  "message": "Invalid MQTT OpenAPI request"
}
```

请求响应必须通过 `msgId` 关联，并根据 `code` 判断是否成功。推送消息的 `msgId` 由 Studio 生成，不对应某条订阅请求。

## 投递与重试规则

- 单条 MQTT OpenAPI 请求不能超过 256 KiB。
- 同一逻辑 `clientId` 的请求按 Broker 到达顺序处理，不同逻辑客户端可以并行处理。
- 未收到响应时，使用原 `msgId` 重试同一逻辑操作。在确认实际操作状态前，不要改用新 `msgId` 重复执行。
- Studio 会暂时复用写请求的最终响应，避免 QoS 1 重投造成同一修改重复执行。不同写请求复用同一 `msgId` 时会返回错误。
- 重连时使用 clean session，并主动重试未收到结果的请求；不要依赖 Broker 在 Studio 断线期间积压控制请求。
