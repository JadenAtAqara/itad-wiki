# HTTP Push 推送

Aqara Studio 支持通过 HTTP Push 将设备数据、对象事件和告警实时推送到第三方系统。您只需在 Studio 中配置一个全局 Webhook 地址，Studio 就会以 HTTP `POST` 的方式，将消息逐条发送到该地址。

这类能力适合以下场景：
- 将设备数据同步到自建平台、数据中台或告警中心。
- 在第三方系统中接收设备新增、删除、空间变更等对象事件。
- 通过服务端回调实现与 BI、工单、消息通知等系统的联动。

## 工作方式

HTTP Push 采用“Studio 主动推送，第三方服务端确认”的模式：

1. 您在 Aqara Studio 中配置一个唯一的接收地址。
2. Studio 按订阅规则向该地址发送 HTTP `POST` 请求。
3. 每个请求正文只包含一条消息，消息格式为 JSON。
4. 第三方接收端完成处理后，返回 JSON 确认结果。
5. 只有同时满足 HTTP 状态码为 `2xx` 且响应 JSON 顶层 `code` 为整数 `0`，本次投递才视为成功。

:::tip
HTTP Push 是实时、best-effort 的推送机制，不提供持久化消息队列、历史补发，也不保证全局顺序。
:::

## 接入要求

在实现接收端前，请先确认以下约束：

| 项目 | 要求 |
| --- | --- |
| 协议 | 支持 HTTP 或 HTTPS |
| HTTP 版本 | HTTP/1.1 |
| 接收地址 | 在 Studio 中配置唯一全局 endpoint |
| HTTPS | 必须能正确校验证书 |
| 重定向 | 不跟随重定向 |
| URL 限制 | 地址中不能包含 query、fragment 和 userinfo |
| 路径处理 | 保留路径中的连续斜杠和已有百分号转义 |

另外，接收端必须支持 `WebhookVerification` 验证请求。保存配置时，Studio 会自动验证当前配置；只有验证成功后，HTTP Push 才会正式启用。后续如果重新启用推送，也会再次执行验证。

## 支持的消息类型

HTTP Push 会向接收端发送以下几类消息：

| 消息类型 | 说明 |
| --- | --- |
| `TraitValueUpdate` | 设备功能点值变化消息 |
| `objectEvent` | 对象事件，例如设备新增、删除、空间变化、自动化变化等 |
| `AlarmEvent` | 告警消息 |
| `WebhookVerification` | Webhook 验证消息，用于校验接收端是否可用 |

业务消息正文复用了 WebSocket `v1` 的消息 schema。除验证消息外，业务消息通常都带有以下通用字段：

| 字段 | 说明 |
| --- | --- |
| `type` | 消息类型，例如 `TraitValueUpdate`、`objectEvent`、`AlarmEvent` |
| `version` | 当前仅支持 `v1` |
| `msgId` | 消息标识，用于链路追踪 |
| `data` | 业务数据主体 |
| `code` | 处理结果码，`0` 表示成功 |
| `message` | 处理结果描述 |

## 请求格式

Studio 向接收端发送请求时，具有以下固定特征：

- 请求方法为 `POST`。
- 默认 `Content-Type` 为 `application/json`。
- 每个请求正文只包含一条消息。
- 响应也在同一条 HTTP 请求中返回。
- 您在 Studio 中配置的固定 Header，会按名称和值原样发送。

### 请求头

HTTP Push 请求头至少包含以下字段：

| Header | 是否必带 | 说明 |
| --- | --- | --- |
| `X-Studio-Delivery-Id` | 是 | 每次投递的唯一标识，格式为 UUID |
| `X-Studio-App-Key` | 按需 | 开启签名时携带 |
| `X-Studio-Time` | 按需 | 开启签名时携带，Unix 毫秒时间戳 |
| `X-Studio-Nonce` | 按需 | 开启签名时携带，32 位小写十六进制随机数 |
| `X-Studio-Sign-Version` | 按需 | 开启签名时固定为 `v1` |
| `X-Studio-Sign` | 按需 | 开启签名时携带，HMAC-SHA256 小写十六进制结果 |

:::note
如果启用了签名，上述 5 个签名相关 Header 必须同时出现，不会只发送其中一部分。
:::

### 验签规则

开启签名后，接收端应使用第三方提供的 `AppSecret` 对请求进行验签。签名原文为以下 6 行 UTF-8 文本，并使用 `LF` 连接，末尾没有换行：

```text
v1
AppKey
Delivery-Id
Time
Nonce
SHA256(raw-body)
```

其中：
- `AppKey` 对应 `X-Studio-App-Key`
- `Delivery-Id` 对应 `X-Studio-Delivery-Id`
- `Time` 对应 `X-Studio-Time`
- `Nonce` 对应 `X-Studio-Nonce`
- `SHA256(raw-body)` 是原始请求体的 SHA-256 小写十六进制值

最终签名算法为：`HMAC-SHA256(signingString, AppSecret)`，并输出小写十六进制字符串，与 `X-Studio-Sign` 比较。

:::tip
发生重试时，消息正文和 `X-Studio-Delivery-Id` 保持不变，但 `Time`、`Nonce` 和 `Sign` 会重新生成。
:::

## 响应要求

接收端返回的响应必须满足以下条件，Studio 才会认定投递成功：

- HTTP 状态码为 `2xx`
- 响应体是未压缩的 UTF-8 JSON
- JSON 顶层 `code` 字段的词法值必须是整数 `0`

以下值都**不算成功**：
- `0.0`
- `0e0`
- `"0"`
- `null`

### 响应体格式

响应体至少应包含：

```json
{
  "code": 0
}
```

验证请求的响应则必须原样回传 `challenge`：

```json
{
  "code": 0,
  "challenge": "00112233445566778899aabbccddeeff"
}
```

如果处理失败，可以返回非 0 的 `code`：

```json
{
  "code": 1
}
```

### 响应体限制

| 项目 | 限制 |
| --- | --- |
| 默认响应体上限 | 4096 字节 |
| 响应体硬上限 | 65536 字节 |
| JSON 最大嵌套深度 | 128（含根对象） |

建议接收端尽量返回简洁响应，避免复杂 JSON 结构和大量响应头。

## Webhook 验证

保存 HTTP Push 配置或重新启用推送时，Studio 会先发送一条 `WebhookVerification` 消息，用于验证接收端是否可用。

验证消息示例如下：

```json
{
  "type": "WebhookVerification",
  "version": "v1",
  "msgId": "verify-39c63800-c8c1-4f4b-b77c-57f24f0de240",
  "data": {
    "challenge": "00112233445566778899aabbccddeeff"
  }
}
```

接收端收到后，应返回：

```json
{
  "code": 0,
  "challenge": "00112233445566778899aabbccddeeff"
}
```

:::note
验证消息不重试。如果验证失败，当前配置不会生效。
:::

## 订阅与默认推送规则

HTTP Push 启用后，并不是所有事件都需要手动勾选才会发送。当前规则如下：

| 类别 | 规则 |
| --- | --- |
| `DEVICE_ADDED` / `DEVICE_REMOVED` | 默认发送，不受其他订阅项影响 |
| `TraitValueUpdate` | 默认开启 |
| `DEVICE_ENDPOINT_ADDED` / `DEVICE_ENDPOINT_REMOVED` | 与设备数据/结构事件组合项共用，默认开启 |
| `DEVICE_TRAIT_PARAMETER_UPDATE` | 与设备数据/结构事件组合项共用，默认开启 |
| 可配置对象事件 | 当前可逐项选择 8 个对象事件，默认全部选中 |
| 告警事件 | 默认关闭 |

补充说明：
- 允许取消全部可选项。此时仍会继续推送 `DEVICE_ADDED` 和 `DEVICE_REMOVED`。
- “全订阅”不仅包含当前所有可选对象事件，也包含后续新增的对象事件。
- 如果关闭 HTTP Push，则默认事件也会一并停止推送。

## 重试、超时与熔断

为避免接收端故障导致大量积压，HTTP Push 采用了明确的超时、重试和熔断策略。

### 重试规则

- 单条业务消息最多重试一次。
- 普通失败场景下，重试前等待 1 秒。
- 如果接收到 `429` 响应，则只接受 `Retry-After` 为 `0` 到 `30` 秒之间的整数值。
- 验证消息不重试。

### 超时规则

| 项目 | 值 |
| --- | --- |
| 连接超时 | 2 秒 |
| 单次 HTTP 调用取消期限 | 5 秒 |
| 逻辑投递窗口 | 45 秒 |

其中，45 秒逻辑投递窗口从消息进入发送阶段开始计算，不包含此前的排队等待时间。窗口到期后，不再启动重试。

:::note
上述时间限制并不代表底层网络资源会立即释放。例如 DNS 等底层操作如果不响应取消，实际结束时间可能更晚。
:::

### 熔断规则

- 连续 5 条消息最终失败后，触发熔断。
- 探测退避时间依次为：1 分钟、5 分钟、15 分钟、1 小时、6 小时，之后封顶。
- 熔断恢复后，不会补发熔断期间错过的历史消息。
- 连续 10 条业务消息投递成功后，退避档位会被重置。

## 数据大小限制

| 项目 | 限制 |
| --- | --- |
| 固定 Header 总容量 | 32 KiB |
| 单条业务请求体默认上限 | 1 MiB |
| 单条业务请求体硬上限 | 64 MiB |

如果消息体超过上限，该消息不会被发送。

## 接收端实现建议

为了让 HTTP Push 更稳定，建议您的接收端遵循以下实践：

- 优先做到“快速接收、异步处理”，避免在 5 秒超时窗口内执行耗时业务。
- 以 `X-Studio-Delivery-Id` 作为投递链路追踪字段，并结合业务状态做幂等处理。
- 不要依赖全局顺序，也不要假设一定能收到历史补发。
- 开启签名时，务必使用原始请求体参与摘要计算，不要使用格式化后的 JSON。
- 对 `WebhookVerification` 单独处理，确保 `challenge` 原样返回。

## 示例

下面是一个典型的推送与确认示例。

### Studio 推送请求

```http
POST /hook HTTP/1.1
Content-Type: application/json
X-Studio-Delivery-Id: 0c9c109a-e724-469c-ae96-1f96e824c127

{
  "type": "WebhookVerification",
  "version": "v1",
  "msgId": "verify-39c63800-c8c1-4f4b-b77c-57f24f0de240",
  "data": {
    "challenge": "00112233445566778899aabbccddeeff"
  }
}
```

### 接收端返回确认

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "code": 0,
  "challenge": "00112233445566778899aabbccddeeff"
}
```

## 小结

HTTP Push 的核心可以概括为三点：

- Studio 负责实时推送，第三方系统负责可靠接收和确认。
- 成功标准非常明确：HTTP `2xx` 加上 JSON `code: 0`。
- 为了保证安全和稳定性，接入方需要同时处理验证、验签、幂等、超时、重试和熔断策略。

如果您正在对接第三方平台，建议先完成最小接入闭环：
1. 部署一个可公网或局域网访问的 Webhook 接口。
2. 正确处理 `WebhookVerification`。
3. 返回符合要求的确认 JSON。
4. 再逐步补充验签、幂等和异步处理能力。
