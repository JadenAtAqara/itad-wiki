# JavaScript for HTTP Integration

HTTP uses `describe`, `encode` and `decode` from the [unified v1 contract](./unified-protocol-script.mdx). The transport module manages the HTTP Client, configured server, TLS, authentication and report Servlet.

## Requests and responses {#messages}

| Encode field | Rule |
| --- | --- |
| `path` | Required, single leading `/`, relative to configured Network server; at most 4096 UTF-8 bytes; no `//`, backslash or control characters |
| `method` | Default GET; GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS |
| `headers` | Object with string values, not a JSON string; at most 64 entries/16 KiB serialized; invalid names and CR/LF/NUL injection are rejected |
| `body` | Optional string, including POST/PUT/PATCH bodies; not legacy postParams |
| `acceptHttpErrors` | Optional Boolean, default false, applies only to this request |

```json title="HTTP encoded message"
{"path":"/devices/demo-1/power","method":"PUT","headers":{"Content-Type":"application/json"},"body":"{\"value\":true}"}
```

Real client responses supply body, statusCode and headers to decode. Header names are lowercase; values are string arrays preserving duplicates, bounded by 64 names/128 values/16 KiB. Body streaming is bounded by Parser maxMessageBytes, not an unlimited read followed by truncation.

Non-2xx responses fail by default. Set acceptHttpErrors=true only when the vendor puts business results in error responses; decode then decides success. Such a response does not automatically trigger 401 challenge retry. HTTP status is not a substitute for business code=0. Existing redirect behavior remains; metadata describes the final delivered response, not a configurable redirect chain.

Ordinary read/write decode inputs include device/point context. Static discovery has body=null and no real response metadata. Bodies are text; binary bodies, arbitrary-host routing and complete inbound authentication context are unsupported.

Generating an Authorization header is not secure credential injection. Current HTTP public configuration has no generic dedicated password/API Key/Bearer Token store and JS injection path. configSchema/scriptParameters are readable ordinary parameters: never rename or hard-code secrets to bypass this boundary. Vendors needing these credentials require a verified same-version secure provisioning solution; without one, report the gap rather than claiming fully automatic onboarding.

## Discovery and reports {#discovery-and-report}

Device/point discovery may issue real requests or return null from encode and a static list from decode. Devices use `{deviceId,deviceName?,model?}`; Network configuration owns the connection address. **Discover/import devices, then discover/import points**. Static lists still require import.

The existing POST Servlet supplies `{transport:"http",operation:"report",path,body,config}`. Decode must return top-level business deviceId and points. Optional replyBody is the HTTP response text, not legacy responseMsg. Application is limited to the matching device in this Network. Only Network parameters exist before identity is decoded.

Callbacks also need an enabled, reachable WebService and the actual Servlet path for this Network. Current protocol Resource templates do not expose WebService/Servlet configuration; connectionSnapshot reports the listener endpoint, not its path. Never use Open's `/open/api/v1` as a device callback or assume every Network uses `/report`. Provisioning callbacks from scratch or validating inbound auth headers remains a public-capability gap.

Reads, writes and reports share one serialized JS Context per Network. Former report-parser shard settings are retired and do not create parallel independent Contexts.

## Offline-testable demonstration {#example}

This is a **fictional REST device**, not vendor facts. demo-1 exposes GET `/devices/demo-1/power` returning `{"value":true}`, PUT on that path with `{value}` returning `{"ok":true}`, GET `/devices/demo-1/health` returning `{"ok":true}`, and POST reports `{"deviceId":"demo-1","value":true}`.

Configure the server through the Network, without embedding real credentials. The example statically discovers one device/Boolean point and supports probe/read/write/report.

```javascript title="Complete HTTP demonstration"
(function () {
    "use strict";
    function describe() {
        return {contractVersion: 1, scriptVersion: "V1.0",
                protocol: {stateSyncMode: "query"}};
    }
    function encode(r) {
        if (r.deviceId !== "demo-1") return null;
        if (r.operation === "probe") return {path: "/devices/demo-1/health"};
        if (r.pointId !== "power") return null;
        if (r.operation === "read") return {path: "/devices/demo-1/power"};
        if (r.operation === "write") {
            if (typeof r.value !== "boolean") throw new Error("Expected Boolean");
            return {path: "/devices/demo-1/power", method: "PUT",
                    headers: {"Content-Type": "application/json"},
                    body: JSON.stringify({value: r.value})};
        }
        return null;
    }
    function decode(m) {
        if (m.operation === "discoverDevices") {
            return {devices: [{deviceId: "demo-1", deviceName: "REST demo"}]};
        }
        if (m.operation === "discoverPoints") {
            return {pointDefinitions: m.deviceId === "demo-1" ? [
                {pointId: "power", pointName: "Power", dataType: "bool", access: 7}
            ] : []};
        }
        var j;
        try { j = JSON.parse(m.body || "{}"); } catch (_) { j = null; }
        if (m.operation === "report") {
            if (!j || j.deviceId !== "demo-1" || typeof j.value !== "boolean") {
                return {operation: "ignore"};
            }
            return {deviceId: j.deviceId, points: [{pointId: "power", value: j.value}],
                    replyBody: "{\"accepted\":true}"};
        }
        if (m.deviceId !== "demo-1") return {operation: "ignore"};
        if (m.operation === "read" && m.pointId === "power") {
            if (!j || typeof j.value !== "boolean") {
                return {code: 1, points: [], errorMsg: "Missing power value"};
            }
            return {points: [{pointId: "power", value: j.value}]};
        }
        if (m.operation === "write" || m.operation === "probe") {
            return {code: j && j.ok === true ? 0 : 1};
        }
        return {operation: "ignore"};
    }
    globalThis.describe = describe;
    globalThis.encode = encode;
    globalThis.decode = decode;
})();
```

```json title="validateScript fixtures"
  {"entry":"decode","input":{"transport":"http","operation":"read","deviceId":"demo-1","pointId":"power","body":"{\"value\":true}","statusCode":200,"headers":{}},"expected":{"operation":"read","points":[{"pointId":"power","value":true}]}}
]
```

## Commands, diagnostics and limits {#debugging}

HTTP supports Spec Command/customSchema using write encoding, fieldId JSON-string value and explicit business code. Status 200 alone does not prove execution.

Debug sessions support probe/read/write, business ACK, state observation and report waiting, subject to instance capabilities. HTTP send only confirms a response was received. Timeout/no response may leave sent=null; do not automatically resend. An over-limit body can prove response receipt, not ACK.

connectionSnapshot REQUEST_READY means a Client is available. reportReceiverEnabled/reportListener describe a component and configured endpoint, not vendor or public reachability. Inbound headers/auth context, binary bodies and script-selected arbitrary hosts remain unsupported.

Normal HttpDevice.doProbe currently marks the device healthy without sending the script's probe request. The actual encode(probe) → HTTP → decode(probe) business check is provided by Open probeOnce. Neither the device's Online label nor REQUEST_READY alone proves vendor reachability or a successful business probe.

TrafficLog is separate from bounded debug capture. Persistent logs can contain redacted/truncated request summaries and response bodies; do not call them payload-free. Prefer [metadata/sanitized sessions](./protocol-script-mcp-api.mdx#payload) for remote diagnostics.
