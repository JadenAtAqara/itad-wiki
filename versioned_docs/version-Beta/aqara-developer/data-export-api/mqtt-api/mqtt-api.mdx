# MQTT API

With the MQTT export feature, you can use an MQTT Broker to send request messages via publish/subscribe and call the [available data export HTTP APIs](#call-an-http-api). You can also implement heartbeat keep-alive, subscribe or unsubscribe to device data, and receive device data changes and other object events.

## Obtain MQTT Connection Information

Before you start publishing or subscribing to request messages, enable the MQTT Export service in Aqara Studio, select a local Broker or a third-party Broker, and obtain the MQTT connection information. For the related process, see [Data Export by MQTT](./../../../aqara-studio/data-export-by-mqtt.mdx).

## Authentication

MQTT channel authentication and topic access are enforced by the Broker connection credentials and ACL. You do not need to provide an OpenAPI Token, nor need to send a `AuthRequest` message for authentication when using MQTT.

For production deployments, you should configure the Broker ACL so that your application can only publish to its assigned request topic and subscribe to its assigned response topic. 

Do not grant an application access to `/open/api/v1/response/+`.

## Topics

| Topic Type | Direction | Format | Purpose |
| --- | --- | --- | --- |
| Request Topic | Application to Studio | `/open/api/v1/request/{clientId}` | API requests, heartbeat, subscribe, and unsubscribe messages |
| Response Topic | Studio to application | `/open/api/v1/response/{clientId}` | API responses, subscription responses, push messages, and errors |

:::tip
The leading `/` in the request Topic and response Topic is part of the Topic name and must not be omitted.
:::

`clientId` identifies a third-party application's logical session and response route in the new MQTT channel. In the usual case, one MQTT connection represents one application, and the application should use the MQTT Client ID submitted in its `CONNECT` packet as the `{clientId}` in the topic.

The `{clientId}` in the topic is not the Client ID configured for Aqara Studio under **MQTT Export**. Studio uses its own single MQTT connection to serve multiple third-party applications, so these two values should not be the same. The topic `{clientId}` may differ from an MQTT connection's Client ID only when a proxy uses one connection for multiple logical clients. In production, use the Broker ACL to restrict the request and response topics available to each application.

`clientId` must contain 1–128 characters and may only contain letters, digits, `.`, `_`, `:`, and `-`.

## Quality of Service

Use QoS 1 for request publication and response subscription. 

Subscribe to the response topic before publishing a request so that an immediate response is not missed.

## Call an HTTP API

To call the [following available data export HTTP APIs](./../introduction.mdx#http-api-list):
- [Space-related APIs](./../introduction.mdx#space)
- [Device-related APIs](./../introduction.mdx#device)
- [Automation-related APIs](./../introduction.mdx#automation)

Write and send a request message with `type` set to `OpenApiRequest`.

### Request fields

| Field | Required | Description |
| --- | --- | --- |
| `type` | Yes | Fixed value: `OpenApiRequest`. |
| `version` | Yes | Fixed value: `v1`. |
| `msgId` | Yes | Request identifier. The response uses the same value. It must contain 1–128 letters, digits, `.`, `_`, `:`, `@`, or `-`. Use a new value for each logical operation and keep it unchanged when retrying that operation. |
| `data.method` | Yes | `GET`, `POST`, `PATCH`, or `DELETE`. |
| `data.path` | Yes | An MQTT-enabled path under `/open/api/v1/`. Do not append a query string or fragment. |
| `data.query` | No | Query parameters as an object. A value may be a string, number, boolean, or an array of those primitive values. |
| `data.headers` | No | Optional OpenAPI metadata headers such as `Lang`. Do not include `Authorization` or Cookie headers. The routing `ClientId` is taken from the topic and cannot be overridden here. |
| `data.body` | No | JSON request body. Omit it or use `null` when the endpoint has no body. |

### Request example

```json
{
  "type": "OpenApiRequest",
  "version": "v1",
  "msgId": "devices-001",
  "data": {
    "method": "GET",
    "path": "/open/api/v1/devices",
    "query": {
      "pageNum": 1,
      "pageSize": 20
    },
    "headers": {
      "Lang": "en-US"
    },
    "body": null
  }
}
```

### Response example

The response topic receives the standard HTTP OpenAPI response body directly, without an additional MQTT wrapper:

```json
{
  "type": "GetDeviceInfoResponse",
  "version": "v1",
  "msgId": "devices-001",
  "code": 0,
  "message": "success",
  "data": {
    "totalCount": 1,
    "pageNum": 1,
    "pageSize": 20,
    "data": []
  }
}
```

## Heartbeat and subscription lease renewal

MQTT Keep Alive maintains the connection between an MQTT client and the Broker. The MQTT SDK normally sends `PINGREQ` packets and handles `PINGRESP` packets automatically. An application does not need to publish the JSON `ping` below merely to keep its Broker connection alive.

The `ping` described here is a Studio application-level **logical subscription lease renewal message**. It tells Studio that the `clientId` associated with the request topic is still using its previously established data subscriptions. Apply the following rules:

- A client that only calls OpenAPI endpoints and has not established a data subscription does not need to send periodic `ping` messages.
- While a data subscription is active, any request received on that `clientId` request topic renews the subscription. If another request has been sent within the last 30 seconds, an additional `ping` is unnecessary.
- When an active subscription is idle and there are no other requests to renew it, send a `ping` at least once every 30 seconds.
- Studio renews the lease only from messages received on the request topic. Receiving push messages does not renew the subscription.
- If Studio receives no message on the request topic for 90 consecutive seconds, the logical session expires. Studio removes all subscriptions for that `clientId` and stops their push messages. Sending `ping` after expiration creates a new logical session but does not restore removed subscriptions; the client must send the relevant subscription requests again.

MQTT Keep Alive and Studio logical subscription lease renewal are independent and cannot replace each other. Configure MQTT Keep Alive separately according to the MQTT SDK and Broker being used.

Request:

```json
{
  "type": "ping",
  "version": "v1",
  "msgId": "ping-001",
  "data": null
}
```

Response:

```json
{
  "type": "pong",
  "version": "v1",
  "msgId": "ping-001",
  "data": "pong",
  "code": 0,
  "message": "success"
}
```

Receiving the matching `pong` confirms that the application message path from the client through the Broker to Studio and back is currently available. If no `pong` is received, check the MQTT connection and retry with the original `msgId`. If the idle period might have exceeded 90 seconds, subscribe again after the message path recovers.

## Subscribe to device data

### Subscribe to all or selected devices

Use `SubscribeAllRequest`. Set `data` to `null`, omit it, or use an empty array to subscribe to all accessible devices. Set it to a non-empty device ID array to subscribe to selected devices.

```json
{
  "type": "SubscribeAllRequest",
  "version": "v1",
  "msgId": "subscribe-devices-001",
  "data": ["device-001", "device-002"]
}
```

Studio returns `SubscribeAllResponse`. To cancel, send `UnsubscribeAllRequest` with the device IDs to remove, or with `data` set to `null` or an empty array to cancel all device-data subscriptions for this logical session.

`SubscribeAllRequest` replaces the session's trait-only subscriptions. `UnsubscribeAllRequest` only changes device-data and Trait subscriptions; independent event and object-event subscriptions must be canceled with their corresponding unsubscribe messages.

### Subscribe to selected Trait values

```json
{
  "type": "SubscribeTraitValueRequest",
  "version": "v1",
  "msgId": "subscribe-trait-001",
  "data": [
    {
      "deviceId": "device-001",
      "endpointId": 1,
      "functionCode": "Light",
      "traitCodes": ["OnOff"]
    }
  ]
}
```

Studio returns `SubscribeTraitValueResponse`. Send the same item structure with type `UnsubscribeTraitValueRequest` to cancel selected Trait subscriptions. A successful subscription or unsubscription response has `code: 0`; it does not contain the current Trait value.

## Subscribe to events

### Alarm events

The independent event channel currently supports `ALARM`:

```json
{
  "type": "SubscribeEventRequest",
  "version": "v1",
  "msgId": "subscribe-alarm-001",
  "data": ["ALARM"]
}
```

Studio returns `SubscribeEventResponse`. Use `UnsubscribeEventRequest` with `data: ["ALARM"]` to cancel it.

### Object events

Use object-event subscriptions for device, space, and automation changes. An omitted, `null`, or empty `objectIds` collection means all accessible objects matching the specified event types.

```json
{
  "type": "SubscribeObjectEventRequest",
  "version": "v1",
  "msgId": "subscribe-object-001",
  "data": [
    {
      "eventTypes": ["SPACE_UPDATED", "AUTOMATION_UPDATED"],
      "objectIds": []
    }
  ]
}
```

Studio returns `SubscribeObjectEventResponse`. Use `UnsubscribeObjectEventRequest` with the same item structure to cancel matching rules. Empty `objectIds` removes all object rules for the specified event types.

The event types accepted by `SubscribeObjectEventRequest` are:

- Device-space relationship: `DEVICE_SPACE_UPDATED`
- Space: `SPACE_ADDED`, `SPACE_REMOVED`, `SPACE_UPDATED`
- Automation: `AUTOMATION_ADDED`, `AUTOMATION_REMOVED`, `AUTOMATION_UPDATED`, `AUTOMATION_SPACE_UPDATED`

When `objectIds` is non-empty, all `eventTypes` in the same item must belong to the same object category. Added events only support subscribing to all accessible objects.

## Push messages

All push messages are published to `/open/api/v1/response/{clientId}`.

### Trait value update

```json
{
  "type": "TraitValueUpdate",
  "version": "v1",
  "msgId": "1754469720110",
  "data": [
    {
      "deviceId": "device-001",
      "endpointId": 1,
      "functionCode": "Light",
      "traitCode": "OnOff",
      "value": true,
      "time": 1754469720110
    }
  ],
  "code": 0,
  "message": ""
}
```

The value type is defined by the corresponding Trait. `time` is a Unix timestamp in milliseconds.

### Object event

```json
{
  "type": "objectEvent",
  "version": "v1",
  "msgId": "object-event-001",
  "data": {
    "eventType": "SPACE_UPDATED",
    "objectId": "space-001",
    "time": 1754469720110,
    "data": {
      "spaceId": "space-001",
      "name": "Living Room",
      "spatialMarking": "room"
    }
  },
  "code": 0,
  "message": "success"
}
```

The nested `data.data` shape depends on `eventType`. Use `eventType` and `objectId` to route the event before parsing its event-specific content.

Device-data subscriptions may additionally receive `objectEvent` pushes with `DEVICE_ADDED`, `DEVICE_REMOVED`, `DEVICE_ENDPOINT_ADDED`, `DEVICE_ENDPOINT_REMOVED`, or `DEVICE_TRAIT_PARAMETER_UPDATE`. These device event types are produced by `SubscribeAllRequest` or matching Trait subscriptions and are not accepted by `SubscribeObjectEventRequest`.

### Alarm event

```json
{
  "type": "AlarmEvent",
  "version": "v1",
  "msgId": "alarm-notify-alarm-001",
  "data": {
    "uuid": "alarm-001",
    "deviceName": "Leak Sensor",
    "deviceId": "device-001",
    "devicePointName": "Leak status",
    "alarmClass": "critical",
    "alarmRuleName": "Water leak alarm",
    "alarmText": "Water leak detected",
    "alarmValue": "true",
    "sourceState": "active",
    "alarmTime": 1754469720110,
    "localized": {}
  },
  "code": 0,
  "message": "success"
}
```

### Error response

Malformed messages, unsupported message types, unavailable routes, and business errors return `ErrorMessage`:

```json
{
  "type": "ErrorMessage",
  "version": "v1",
  "msgId": "devices-001",
  "data": null,
  "code": 400,
  "message": "Invalid MQTT OpenAPI request"
}
```

Always correlate a request response by `msgId` and determine success from `code`. Push-message `msgId` values are generated by Studio and do not correspond to a subscription request.

## Delivery and retry rules

- A single MQTT OpenAPI request must not exceed 256 KiB.
- Requests from the same logical `clientId` are processed in Broker arrival order. Different logical clients may be processed concurrently.
- If no response is received, retry the same logical operation with the same `msgId`. Do not assign a new `msgId` until the actual operation state has been reconciled.
- Studio temporarily reuses the final response for write requests to prevent a QoS 1 redelivery from executing the same mutation twice. Reusing a `msgId` for a different write request returns an error.
- Reconnect with a clean session and actively retry requests whose result was not received. Do not rely on the Broker to queue control requests while Studio is disconnected.
